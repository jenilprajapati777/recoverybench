## What is RecoveryBench?

RecoveryBench is a local-first testing platform for autonomous AI agents that perform real-world side effects (charging credit cards, reserving resources, updating external databases, dispatching webhooks).

When an external tool call experiences a network timeout or dropped response after the server commits a mutation (the classic Two Generals' Hazard), naive agent retry loops frequently cause duplicate side effects—such as double-charging a customer.

RecoveryBench injects deterministic distributed systems faults into agent tool workflows, tracks every mutation attempt in an append-only effect ledger, and verifies whether your agent recovers safely without creating duplicate, missing, or orphaned side effects.

### Supported Framework Integrations
- **Generic Python Callables:** Test arbitrary functions, methods, or classes using `@agent` or `wrap_agent()`.
- **LangGraph Adapter:** Native integration bridging LangGraph `StateGraph` workflows and `ToolNode` instances.
- *(Roadmap):* Dedicated adapters for CrewAI, AutoGen, and Model Context Protocol (MCP) tool servers.

## The Problem: The Two Generals' Hazard in AI Agents

When an autonomous AI agent interacts with the real world (charging cards, reserving seats, provisioning cloud instances, dispatching webhooks), distributed systems failure modes inevitably strike:

1. **Agent issues tool call:** `payment_gateway.charge(amount=100, currency="USD")`
2. **Server commits side effect:** Bank records the transaction and deducts funds.
3. **Response dropped:** A transient network blip drops the TCP ACK or HTTP response.
4. **Agent sees a timeout:** Naive prompt loop says *"Action timed out; let's retry!"*
5. **Agent retries blindly:** A second charge request is issued with a new or missing idempotency key.
6. **Customer double-charged:** **Catastrophic failure in production.**

Existing LLM tools typically focus on **observability** (traces, tokens, latency) or **model quality benchmarks** (evaluating reasoning, MMLU accuracy, hallucination). RecoveryBench complements these frameworks by testing autonomous agent recovery behavior and business side-effect integrity under deterministic distributed faults.

RecoveryBench provides **deterministic fault injection**, an **append-only effect ledger**, and **rule-based recovery assertions** to prove whether your agent recovers safely before code hits production.

## Key Features

- **Deterministic Fault Injection:** Intercept and simulate distributed failure modes:
  - `timeout_after_commit` (The critical Two Generals' hazard)
  - `timeout_before_commit` (Connection timeout before server execution)
  - `duplicate_delivery` (Webhook or queue redelivery)
  - `http_429_then_success` (Rate limits with `Retry-After` backoff)
  - `http_500_transient` (Internal server error followed by recovery)
  - `malformed_tool_response` (Corrupted JSON or schema drift)
- **Reusable Agent Integration Interface:**
  - **Generic Python Callables:** Test arbitrary functions, methods, and lambdas using the `@agent` decorator or `wrap_agent()`.
  - **LangGraph Framework Adapter:** Native integration with LangGraph `StateGraph` workflows, bridging RecoveryBench tools into LangChain `@tool` definitions and intercepting `ToolNode` errors.
- **Append-Only Effect Ledger & Decoupled Transaction Identity:**
  - `operation_id`: Identifies the logical business operation boundary. Stable across retries; distinct for separate operations.
  - `attempt_id`: Unique invocation transmission identifier per attempt (e.g. `att_run123_1`).
  - `effect_id`: Ground-truth persistent mutation identifier generated by the mock service on commit.
  - `request_fingerprint`: Canonical SHA-256 hash of arguments, retained purely as diagnostic metadata (never used as the sole basis for duplicate detection).
- **Deterministic Recovery Evaluator:** Mathematical, rule-based verification with zero flaky LLM-as-a-judge guesswork:
  - Duplicate side-effect detection (flags multiple distinct `effect_id`s under one `operation_id`)
  - Missing side-effect detection
  - Idempotency key stability tracking across retries of an operation
  - Retry budget and circuit breaker enforcement
  - Safe unknown-outcome handling verification
  - False-success / phantom-completion detection and explicit completion verification (`SUCCEEDED`, `FAILED`, `UNKNOWN`)
  - Read-only agent verification (`expected_side_effects: 0`) and prohibited mutation detection
  - Strict boolean validation (rejection of string/integer booleans without coercion) and conflict arbitration
  - Infrastructure error classification (`INFRASTRUCTURE_ERROR`) with automated secret masking and sanitized reports
- **Ground-Truth Evidence Linking:** Every test verdict and assertion cites concrete ledger event IDs, attempt counts, and receipt references.
- **Multi-Format Reporting:**
  - **Interactive HTML Reports:** Collapsible evidence drawers, dark mode dashboard, audit timelines.
  - **Machine-Readable JSON:** Full assertion schemas, metrics, and evidence payloads.
  - **CI/CD JUnit XML:** Native integration with GitHub Actions, GitLab CI, and Jenkins test reporters.
- **Zero-Sleep Virtual Time:** Simulates exponential backoff and retries in milliseconds without wall-clock `time.sleep()`.
- **Container Execution Isolation & Network Controls (`--network=none`):**
  - **Isolated Container Mode (Default):** Runs agents inside Linux containers configured with `--network=none`, dropping all Linux capabilities (`--cap-drop=ALL`), disabling privilege escalation, and restricting resources (RAM, CPU, PIDs).
  - **Zero Credential Leakage:** Staged workspaces strictly omit `.env*`, `.ssh`, `.aws`, `.azure`, `.git`, `.venv`, and certificates before mounting read-only into containers.
  - **Symlink Escape Detection:** Rejects workspaces with external symlink escapes.
  - **Stdio IPC Protocol:** Host-worker communication runs over framed JSON Lines on stdin/stdout; user stdout is redirected to stderr with automated secret redaction.
  - **Fail-Closed Guarantee:** Fails closed (exit code 3) if Docker is unavailable; never silently downgrades to trusted mode.
  - **Trusted In-Process Mode:** Pass `--isolation trusted` for rapid development and unit testing without Docker.
- **Local-First & Offline Execution:** Evaluation and scenario runs execute locally without a cloud control plane, paid API keys, or cloud telemetry; isolated agent containers execute with network disabled (`--network=none`). Initial environment setup (e.g., Python package installation and container runtime image pulling) requires network access.

## The Code Difference: Naive vs. Safe Agent

```python
# Unsafe Naive Agent (src/recoverybench/agent/naive.py)
# On retry, generates a brand-new random key or omits the key:
flawed_key = f"key_{uuid.uuid4().hex[:8]}"
tool_call("payment_gateway", "charge", task.task_params, flawed_key)
# Result: Gateway treats retry as a second independent transaction -> DOUBLE CHARGE!

# Safe Idempotent Agent (src/recoverybench/agent/idempotent.py)
# Derives a deterministic, stable key across all retries of this transaction:
stable_key = f"idem_{hashlib.sha256(serialized_task).hexdigest()[:16]}"
tool_call("payment_gateway", "charge", task.task_params, stable_key)
# Result: Gateway recognizes retry, returns original receipt -> EXACTLY 1 CHARGE!
```

## CLI Reference & Exit Codes

| Command | Description |
| :--- | :--- |
| `recoverybench init` | Initialize a RecoveryBench configuration and directory structure. |
| `recoverybench doctor` | Check environment, Docker daemon, container readiness, and sandbox limits. |
| `recoverybench list-scenarios` | List registered built-in and local YAML recovery scenarios. |
| `recoverybench validate <path>` | Validate scenario YAML syntax and semantic rules without executing. |
| `recoverybench demo [--isolation trusted]` | Run comparative demo of naive vs. safe agents (trusted by default). |
| `recoverybench run <scenario> [--isolation isolated\|trusted]` | Run a recovery test with isolated container or trusted execution. |
| `recoverybench suite <dir> [--isolation isolated\|trusted]` | Batch execute scenario suite in isolated container or trusted mode. |
| `recoverybench replay <run-id>` | Replay a recorded event trace from the SQLite ledger. |
| `recoverybench report <run-id>` | Generate reports (`--format json`, `html`, `junit`, `both`, `all`). |

### Standard CLI Exit Codes

RecoveryBench strictly uses deterministic exit codes for CI/CD pipelines:

- `0` (`EXIT_PASS`): All assertions passed. Agent recovered safely.
- `1` (`EXIT_RECOVERY_FAILED`): One or more recovery assertions failed (e.g. duplicate side-effect).
- `2` (`EXIT_CONFIG_ERROR`): Configuration syntax error, invalid scenario schema, or file not found.
- `3` (`EXIT_INFRASTRUCTURE_ERROR`): System crash, database failure, or unhandled runtime error.

## Python SDK & Framework Integration

See the complete [SDK Integration Guide](docs/SDK_INTEGRATION_GUIDE.md) for detailed patterns and architecture.

### 1. Testing Generic Python Functions

Test arbitrary agent functions with the `@agent` decorator:

```python
import recoverybench as rb
from recoverybench.agent.base import AgentResult, TaskContext, ToolCaller


@rb.agent(id="resilient_billing_agent")
def my_agent(task: TaskContext, tool_call: ToolCaller) -> AgentResult:
    # Use stable idempotency key across retries
    key = "tx_stable_key_001"
    for attempt in range(1, 4):
        try:
            res = tool_call("payment_gateway", "charge", task.task_params, key)
            return AgentResult(success=True, data=res, attempts=attempt)
        except Exception:
            continue
    return AgentResult(success=False, error="Exhausted retries")


# Run single-line recovery test
result = rb.test_agent("payment_timeout_after_commit", my_agent)
assert result.passed
assert result.verdict == "PASS"
```

### 2. Testing LangGraph StateGraph Agents

Test real LangGraph workflows using native tool bridging and `ToolNode`:

```python
import recoverybench as rb
from recoverybench.adapters.langgraph import IdempotentLangGraphAgent, NaiveLangGraphAgent

# Resilient LangGraph agent (stores idempotency key in graph state)
safe_agent = IdempotentLangGraphAgent()
result = rb.test_agent("payment_timeout_after_commit", safe_agent)
assert result.passed
assert result.evaluation.actual_side_effects == 1

# Naive LangGraph agent (blindly retries without stable key)
naive_agent = NaiveLangGraphAgent()
fail_result = rb.test_agent("payment_timeout_after_commit", naive_agent)
assert not fail_result.passed
assert fail_result.evaluation.duplicate_effect_count == 1  # Double charge detected!
```

## Supported Fault Scenarios

RecoveryBench includes 6 deterministic fault injection scenarios:

| Scenario ID | Fault Mode | Real-World Failure Mode Simulated |
| :--- | :--- | :--- |
| `payment_timeout_after_commit` | `timeout_after_commit` | **Two Generals' Hazard:** Server mutates database state, but the network acknowledgment packet drops before reaching the client. |
| `payment_timeout_before_commit` | `timeout_before_commit` | Gateway connection timeout before the request reached or committed on the service. |
| `payment_duplicate_delivery` | `duplicate_delivery` | Message queue or webhook redelivery triggering multiple incoming execution triggers. |
| `payment_rate_limit_429` | `http_429_then_success` | Upstream API rate limit with `Retry-After: 2` header before returning 200 OK. |
| `payment_http_500_transient` | `http_500_transient` | Upstream 500 Internal Server Error for initial $N$ attempts before recovering. |
| `payment_malformed_response` | `malformed_tool_response` | Tool returns corrupted JSON, missing fields, or empty strings testing parser robustness. |

## Defining Scenarios (YAML & JSON)

Scenarios are declarative YAML (or JSON) files. Every scenario must specify `schema_version: 1`:

```yaml
schema_version: 1
scenario_id: payment_timeout_after_commit
name: "Payment Timeout After Commit (Two Generals' Hazard)"
description: "Gateway commits charge but response drops; tests duplicate charge prevention."
target_tool: payment_gateway
target_action: charge
seed: 42

faults:
  - type: timeout_after_commit
    target_tool: payment_gateway
    target_action: charge
    failure_count: 1
    error_message: "Network connection lost after bank transaction processing"

task:
  amount: 5000
  currency: USD
  customer_id: "cust_demo_alice_99"

assertions:
  expected_side_effects: 1
  max_duplicate_effects: 0
  require_stable_idempotency_key: true
  max_allowed_retries: 3
  expect_agent_success: true
```

> **Schema Versioning & Compatibility Notice:**
> - `schema_version: 1` is strictly required. Unversioned scenario files are **not** backward-compatible and will fail validation.
> - Schema version 1 is supported by all RecoveryBench releases that explicitly maintain support for schema version 1.
> - The Python SDK `load_scenario("path/to/scenario.(yaml|yml|json)")` entry point dynamically validates and loads both YAML and JSON files.

## Recovery Evaluator Rules

RecoveryBench evaluates 5 core invariants from the immutable ledger:

1. **`side_effect_count`:**
   - Verifies `actual_committed == expected_committed` and `duplicate_count <= max_duplicate_effects`.
   - Distinguishes duplicate commits from missing commits.
   - Cites every committed receipt token (`ref='ch_sim_0001'`).
2. **`idempotency_key_stability`:**
   - Computes SHA-256 hashes of idempotency keys for every attempt.
   - Asserts that subsequent retry attempts reuse the initial attempt's key hash.
3. **`retry_budget`:**
   - Calculates observed retry count across events.
   - Asserts agent did not exceed `max_retries_allowed` or trip circuit breaker limits.
4. **`agent_completion_truth`:**
   - Validates that agent's reported `success=True/False` matches actual ledger commits.
   - Detects **phantom success** (agent reports success, but 0 effects committed) and **unreported success** (side effect committed, but agent returned failure).
5. **`unknown_outcome_handling`:**
   - Triggered when ambiguous commit faults occur (`timeout_after_commit`).
   - Asserts that the agent safely reconciled using an idempotent query or re-attempt rather than blindly retrying with a new key.

## CI/CD Integration & GitHub Actions

See the comprehensive [GitHub Actions Guide](docs/GITHUB_ACTIONS_GUIDE.md) for full workflows and configuration.


### GitHub Actions Workflow Example

```yaml
name: Agent Recovery CI
on: [push, pull_request]

jobs:
  test-recovery:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: "pip"
      - run: pip install -e ".[langgraph,dev]"

      - name: Validate Scenarios
        run: recoverybench validate scenarios

      - name: Run RecoveryBench Suite
        run: recoverybench suite scenarios --agent idempotent --output-dir reports --junit

      - name: Publish Test Report
        uses: mikepenz/action-junit-report@v4
        if: always()
        with:
          report_paths: "reports/*_report.xml"

      - name: Upload Report Artifacts
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: recovery-reports
          path: reports/
```

RecoveryBench automatically detects `$GITHUB_STEP_SUMMARY` and writes rich execution tables and failure evidence directly to the GitHub Actions overview tab.

## Security Model

- **Real Kernel & Container Network Isolation:** Agents run inside Linux containers with `--network=none`. Direct outbound TCP/UDP and DNS resolution are blocked at the kernel network namespace level.
- **Shared Kernel Notice:** Containers share the host operating system kernel and are not hardware-virtualized VMs; see [SECURITY_MODEL.md](docs/SECURITY_MODEL.md) for threat modeling, boundary caveats, and kernel sharing details.
- **Controlled Stdio IPC:** Host-worker communication runs strictly over stdin/stdout using framed JSON Lines; agent debug logs to stdout are routed to stderr.
- **Zero Credential Exposure:** Staged workspaces exclude `.env*`, `.ssh`, `.aws`, `.azure`, `.git`, `.venv`, and certificates before mounting read-only (`:ro`).
- **Resource Constraints & Cap Drop:** Hard caps on memory (512MB), CPU (1.0 core), PIDs (64 limit), non-root execution (`nobody:nogroup`), and full capability dropping (`--cap-drop=ALL`).
- **Simulated Tool Environment:** Mocks run strictly in-memory or in isolated SQLite test databases; agents interact with mock tool interfaces rather than live production services.
- **Payload Masking & Hashing:** Idempotency keys, card numbers, and authorization headers are SHA-256 fingerprinted; raw credentials are never logged to ledgers or exported in reports.
- **Local Isolation:** No phone-home network calls, analytics, or remote API dependencies.
- **Fail-Closed Execution:** Any unhandled fault, corrupted configuration, or ambiguous state terminates safely without side effects. If Docker isolation is requested and unavailable, the harness immediately halts with exit code 3.
