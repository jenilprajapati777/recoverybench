## 1. Executive Summary & Original Defect

### 1.1 The Original Defect (AUDIT-01)
In the original implementation of RecoveryBench, duplicate side effects were detected exclusively by grouping committed ledger events by `request_fingerprint`:
```python
# Legacy implementation in rules.py:
fingerprint_commits = Counter(e.request_fingerprint for e in committed_events)
duplicate_count = sum(count - 1 for count in fingerprint_commits.values() if count > 1)
```
Where `request_fingerprint` was computed as:
$$\text{request\_fingerprint} = \text{SHA-256}\left(\text{JSON}(\text{canonical}(\text{tool}, \text{action}, \text{payload} \setminus \{\text{idempotency\_key}, \text{request\_id}\}))\right)[:16]$$

#### The Fundamental Flaw:
The request fingerprint conflated **business payload arguments** with **transactional identity**.
If an agent legitimately executed two independent business operations with identical parameters within the same scenario run (e.g. charging a customer $25.00 for Order A and $25.00 for Order B, or dispatching two identical alert webhooks):
1. Both operations generated the **exact same request fingerprint**.
2. Both operations committed to state, producing 2 committed events with `fp_same`.
3. The legacy evaluator computed $\text{duplicate\_count} = 2 - 1 = 1$, causing the test to **falsely fail** with a duplicate side effect violation!
4. Conversely, if an unsafe retry altered a trivial argument (or if no idempotency key was sent), fingerprinting could not reliably distinguish between a retried transmission and an independent business intent.

## 2. New Decoupled Identity Architecture

To mathematically resolve this distributed systems hazard, RecoveryBench has decoupled identity into three explicit, orthogonal concepts, while preserving `request_fingerprint` purely as diagnostic metadata:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        LOGICAL OPERATION LEVEL                         │
│  operation_id: "op_invoice_101"                                        │
│  - Identifies the logical business boundary.                           │
│  - Stable across all retries of this intended operation.               │
│  - Different for two independent operations, even with matching args. │
└──────────────────┬─────────────────────────────────────────────────────┘
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
┌──────────────────┐ ┌──────────────────┐
│  INVOCATION 1    │ │  INVOCATION 2    │
│  attempt_id:     │ │  attempt_id:     │
│  "att_run1_1"    │ │  "att_run1_2"    │
│  (Dropped ACK)   │ │  (Idempotent)    │
└────────┬─────────┘ └────────┬─────────┘
         │                    │
         └─────────┬──────────┘
                   ▼
┌──────────────────────────────────────┐
│       COMMITTED STATE MUTATION       │
│  effect_id: "eff_ch_sim_0001"        │
│  - Ground-truth committed mutation   │
│    created by mock service.          │
│  - Reused on idempotent replay.      │
│  - 1 unique effect -> 0 duplicates!  │
└──────────────────────────────────────┘
```

### 2.1 The Three Core Identifiers
1. **`operation_id`:**
   - Identifies one logical business operation.
   - Stable across all retries of the same intended operation.
   - Different for two independent operations, even if their payloads are identical.
   - Supplied by the agent (`tool.call(..., operation_id=...)`), or established by the task boundary (`task.operation_id` / `scenario.task["operation_id"]`).
   - Missing `operation_id` on committed events results in an explicit `INSUFFICIENT_EVIDENCE` evaluation verdict; it is never silently guessed from fingerprints.
2. **`attempt_id`:**
   - Identifies one specific invocation attempt.
   - Generated by the `ExecutionEngine` for every invocation (`att_{run_id}_{invocation_number}`).
   - Recorded in every ledger event.
3. **`effect_id`:**
   - Identifies an actual committed mutation in the simulated tool state.
   - Generated only when a new side effect is committed by the mock service (`eff_ch_sim_0001`).
   - Stable when an idempotent retry resolves to the previously committed effect.
   - Never fabricated by the evaluator.
   - Missing `effect_id` on a committed event is treated as an unverified commit and excluded from proven committed effect counts.

### 2.2 Core Invariant for Duplicate Detection
For any given `operation_id`:
$$\text{Duplicates}(\text{operation\_id}) = \max\left(0, |\text{Distinct Committed Effect IDs}(\text{operation\_id})| - 1\right)$$
$$\text{Total Duplicates} = \sum_{\text{op} \in \text{Operations}} \text{Duplicates}(\text{op})$$

- If an operation commits an effect, times out, and retries idempotently returning the existing `effect_id`, the set of distinct effect IDs is $\{\text{eff\_1}\}$:
  $$\text{Duplicates} = 1 - 1 = 0 \quad (\text{PASS})$$
- If an operation retries with a new key and commits a second charge, the set of distinct effect IDs is $\{\text{eff\_1}, \text{eff\_2}\}$:
  $$\text{Duplicates} = 2 - 1 = 1 \quad (\text{FAIL: Double Charge})$$
- If two independent operations `op_1` and `op_2` are executed with identical arguments:
  $$\text{Duplicates}(\text{op\_1}) = 0, \quad \text{Duplicates}(\text{op\_2}) = 0 \implies \text{Total Duplicates} = 0 \quad (\text{PASS})$$

## 3. Schema & Database Migration Details

### 3.1 SQLite Ledger Schema Migration
The `effect_ledger` table was extended with three new nullable columns:
```sql
ALTER TABLE effect_ledger ADD COLUMN operation_id TEXT;
ALTER TABLE effect_ledger ADD COLUMN attempt_id TEXT;
ALTER TABLE effect_ledger ADD COLUMN effect_id TEXT;
```
Indexes were added to support high-performance lookup:
```sql
CREATE INDEX IF NOT EXISTS idx_ledger_op_id ON effect_ledger(operation_id);
CREATE INDEX IF NOT EXISTS idx_ledger_effect_id ON effect_ledger(effect_id);
```

### 3.2 Idempotent Auto-Migration Strategy
In `SQLiteLedger._init_db()`:
1. `PRAGMA table_info(effect_ledger)` is executed to inspect existing columns.
2. If any of `operation_id`, `attempt_id`, or `effect_id` are absent (as in existing databases created prior to P0-1), `ALTER TABLE` is executed idempotently.
3. Indexes on new columns are executed strictly after column validation.
4. Historical records are preserved with `NULL` (None) for the new columns, ensuring zero data loss.
5. Reading historical rows with `NULL` columns returns `LedgerEvent` with `operation_id=None`, which correctly triggers `INSUFFICIENT_EVIDENCE` rather than false passes.

## 7. Remaining Limitations

1. **Agent Explicit Boundary Best Practice:** For single-task scenarios, `operation_id` defaults cleanly to `op_{scenario_id}`. However, when an agent performs *multiple* operations within a single scenario run, the agent developer must pass `operation_id="op_custom"` to `tool.call` to establish separate transaction boundaries. If an agent loops over multiple items without passing distinct operation IDs, all operations share the scenario's default operation ID.
2. **Next Milestone:** P0-2 (Resolving `None` return normalization in `CallableAgentAdapter` and enforcing socket network isolation) remains pending.
